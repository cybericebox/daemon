# feat/hardening: notes for the joint release

## Before the release (TODO)

- **Laboratory pin.** The microVM work reads `CapacityResponse.node_profiles` by field name (`labagent.ProfilesOf`, protoreflect), so the daemon builds on the current pin (v1.7.4). At the joint release laboratory is released first; then bump the pin in `go.mod` and move `ProfilesOf` to the typed getters (`GetNodeProfiles`, `NodeProfileCapacity`). Until then an agent without the field reads as an older agent (container only).
- **Migrations.** 0205/0206 (wave 1), 0207 (device type `container` becomes `node` + profile), 0208 (stored node profile report of each agent). 0207 and 0208 have integration tests (`TestMigration0207TurnsContainersIntoNodes`, `TestAgentNodeProfileReportIsKeptAndOverwritten`) that passed locally.
- **API.** Devices are returned as `Type: "node"` with `Profile`; the frozen frontends do not know it yet (UI pass).
- **PROXY protocol.** `HTTP_SERVER_PROXY_PROTOCOL_FROM` is off by default; the daemon must run with the list set before the edge starts sending the header.
- **Labs after 0207.** The lab definition hash is taken from the topology as stored (`node` + profile); labs created before migration 0207 are recreated once in a test database (no production database exists yet).
- **Reveal cohort.** The «show to all» cohort is recomputed until the event starts (an unopened cohort); from the start it is frozen. The SQL (`FreezeEventLabRevealBarrier`, `ListStandTeams`) was edited by hand in the sqlc output and has Docker integration tests (`reveal_cohort_recompute_integration_test.go`) (they passed locally); sqlc output was edited by hand, so run the sqlc generate check in CI.
- **Reserved device names.** `exerciseModel.ReservedDeviceNames` copies `laboratory/pkg/names.ReservedDeviceNames` (a test compares them when the laboratory source is next to the daemon). After the pin bump, import the laboratory package and delete the copy.
- **Unavailable reason codes.** `infraModel.UnavailableCodes` and `ParseUnavailableReason` copy `laboratory/pkg/names` (`UnavailableReasonCodes`, `ParseUnavailableReason`); a test compares the lists when the laboratory source is next to the daemon. After the pin bump import the package and delete the copy.
- **Catalog import heartbeat (migration 0212).** A running import writes a heartbeat every 30 s; without one for 2 minutes it reads as failed (error 70994 «interrupted»; no written state, so a restarted import resumes and clears it). A daemon stop (SIGTERM, rollout) no longer fails an import: the job returns the error to River (MaxAttempts 5) and runs again after the start from the beginning (stages are idempotent: image pushes are by content, tasks and "done" are one commit). Only a time-out still records failed (70995). `GET /exercises/import/jobs` lists running and failed imports not yet closed, with `State` and `Error`; `DELETE /exercises/import/jobs/{jobID}` closes the row of a failed one (409 while running, 404 for another user's); a rerun shows it again (dismissals table). A job waiting in the queue for a free worker longer than 2 minutes also reads as failed.
- **Queued imports (migration 0220).** An import that no worker has started has stage `queued` and is shown as state `queued`; it has no heartbeat to miss, so it is not interrupted for waiting (only after 6 hours, when the queue has surely lost it). The worker's first write moves it to `unpacking`; the 2-minute heartbeat window applies from then. The migration number leaves room for the other branches (0214-0219).
- **Google sign-in links by verified address.** An unlinked Google identity whose address Google vouches for (email_verified) and equals, normalized, the address of an active account with a confirmed email is linked to it and signs in, with no mail. A blocked, incomplete, unconfirmed or deleted account, no account, and an account that already has a Google identity keep the plain «not registered» answer.
- **DB connections.** `POSTGRES_MAX_CONNS` defaults to 24 (was 32). The advisory-lock sessions (leadership, a push to an agent) keep connections outside the pools: at most 8 per replica (`advisory.MaxHeld`, the rest wait for their context), counted in the budget: per replica main + job + 8 (40 by default). A warning is logged every 15 s while a pool is 80% in use or statements waited or gave up for a connection.
- **Agent features** are read again every minute and when a lab is refused for missing persistence (at most once per 10 s per agent), so persistence that becomes available after the agent started is seen at once.
- **HTTP/3** logs one warning at start when the UDP socket buffers are below 7 MiB, with the sysctl to raise.
- **Google sign-in: Gmail links at once, others confirm (migration 0222).** An unlinked Google identity with a verified address that equals the address of an active account: gmail.com/googlemail.com (confirmed account email, no Google yet) is linked and signed in at once, as before. Any other domain gets no link and no session: the callback sets a short-lived (10 min), single-use ticket in an HttpOnly Secure `__Host-cib_google_link` cookie (never in the URL, so it is bound to the browser that started the flow) and redirects to the ID page `/google-link/`. The owner confirms with the password or a six-digit code mailed to the address (60 s apart, 5 per hour; 5 wrong codes drop the ticket; the sign-in lockout guards the password); an account without a password uses the code only. Only then the identity is linked (the unique index of 0221 guards a race) and the session is created. The page shows the Google account that will be linked (email, name). No mail announces the link; the only mail is the code. New routes `GET/DELETE /api/auth/google/pending`, `POST .../pending/code`, `POST .../pending/confirm`; new errors 20437/30436/70435; new mail type `google_link_code` (startup-seeded).
- **Last sign-in address.** Every successful sign-in (password, Google, Google confirmation, setup) sets the cookie `cib_last_email` (host-only, no Domain, HttpOnly, Secure, SameSite=Lax, one year, kept after sign-out) with the account address. `GET /api/auth/last-email` answers `{Email}` (empty when none), `DELETE` clears it («not you»), deleting the account clears it too, and the Google start uses it as `login_hint` unless the query brings one. Passkey sign-in must call `startSession` instead of `prot.Authenticate` when that branch lands.
